# امنیت: وضعیت فعلی و کار باقی‌مانده

**کد فعلی فقط hash رمز و annotationهای اعلام دسترسی را دارد؛
احراز هویت و اجرای مجوزهای REST هنوز کامل نیست.**
راهنمای قبلی به کلاس‌هایی اشاره می‌کرد که اکنون در پروژه وجود ندارند؛
وضعیت این جدول بر اساس فایل‌های فعلی است.

## جدول تسک‌ها

| تسک | وضعیت | شاهد / کار باقی‌مانده |
|---|---|---|
| تولید و بررسی hash BCrypt | انجام‌شده | `BCryptPasswordHash.generate/verify` |
| hash رمز در ایجاد و ویرایش کاربر | انجام‌شده | `UserServiceImpl` |
| DTO کاربر بدون رمز | انجام‌شده | `UserDto` رمز یا hash ندارد؛ DTO سفارش هنوز entity کاربر دارد |
| SQL نمونهٔ کاربران و گروه‌ها | انجام‌شده | `META-INF/sql/security.sql` شامل viewها و seed است |
| اجرای خودکار SQL امنیت | انجام‌نشده | propertyهای مربوط در persistence کامنت‌اند |
| تنظیم HTTP Basic و Identity Store | انجام‌نشده | `SecurityConfig.java` در کد فعلی نیست |
| datasource امنیت در web.xml | انجام‌نشده | `jdbc/SecurityDS` تعریف نشده است |
| اجرای annotationهای مجوز روی REST | انجام‌نشده | `RolesAllowedFilter.java` در کد فعلی نیست؛ رفتار سرور باید تنظیم و بررسی شود |
| یکدست‌کردن مجوزهای همهٔ ماژول‌ها | ناقص | بعضی APIها annotation دارند، بعضی ندارند |
| تست BCrypt | انجام‌شده | ۴ تست موفق در اجرای ۲۰۲۶/۱۰/۱۳ |
| تست authentication و پاسخ‌های 401/403 | انجام‌نشده | تست فیلتر مجوز وجود ندارد؛ بررسی HTTP هم در این نوبت انجام نشده است |
| حذف entity کاربر از DTO سفارش | انجام‌نشده | مانع انتشار احتمالی hash و داده‌های داخلی شود |

## استفادهٔ فعلی از BCrypt

در service کاربر، `BCryptPasswordHash` inject می‌شود:
`generate(password.toCharArray())` hash می‌سازد و
`verify(password.toCharArray(), storedHash)` آن را بررسی می‌کند.

هر بار salt جدید تولید می‌شود؛ hashها را با هم مقایسه نکنید.
`UserRequest` برای create و update رمز می‌خواهد؛ ویرایش نیز دوباره hash می‌کند.
رمز را در response، log، localStorage یا sessionStorage ننویسید.
محدودیت BCrypt بر حسب بایت است؛ طول ۷۲ کاراکتری ورودی جای بررسی
۷۲ بایت برای متن چندبایتی را نمی‌گیرد.

## معنای annotationهای موجود

| annotation | مقصود در قرارداد API |
|---|---|
| `@PermitAll` | دسترسی عمومی |
| `@RolesAllowed("admin")` | دسترسی نقش admin |
| `@RolesAllowed("attachment:file")` | دسترسی گروه مربوط به فایل پیوست |
| `@DenyAll` | عدم دسترسی |

وجود این annotationها به‌تنهایی تأیید اجرای مجوز در کلاس CDI REST نیست.
ابتدا مکانیزم امنیت سرور و اجرای قواعد تنظیم شود؛ سپس با درخواست واقعی بررسی شود.
ارسال هدر Authorization توسط UI نیز ورود موفق یا مجازبودن کاربر را اثبات نمی‌کند.

## مسیر پیشنهادی تکمیل آموزشی

۱. یک مکانیزم سادهٔ HTTP Basic و خواندن کاربر/گروه از datasource پروژه تنظیم شود.
۲. seed و datasource موردنیاز با جدول‌های فعلی تطبیق داده و سپس فعال شوند.
۳. اجرای مجوزهای annotation در REST مشخص شود؛ منطق login داخل ماژول‌ها تکرار نشود.
۴. GET عمومی، درخواست بدون اعتبار، نقش نامجاز و نقش مجاز روی TomEE بررسی شوند.
۵. DTOهای خارج از ماژول کاربران نیز از انتشار entity کاربر پاک شوند.

`security.sql` نمونهٔ `admin/admin123` و `user/user123` دارد،
اما **با تنظیم فعلی اجرا نمی‌شود**؛ این حساب‌ها را از پیش موجود فرض نکنید.
نام گروه‌های آن از roleها و permissionها خوانده می‌شود.

این پروژه JWT یا سامانهٔ login پیچیده لازم ندارد. HTTP Basic فقط برای محیط
آموزشی محلی در نظر گرفته شود؛ خارج از آن ارسال رمز بدون HTTPS مناسب نیست.
