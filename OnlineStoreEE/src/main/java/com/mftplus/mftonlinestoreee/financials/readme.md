# امور مالی — دستور کار باقی‌مانده

سه بخش: بانک/حساب/تراکنش، صندوق‌دار و پرداخت نقدی/کارتی/چکی.
هدف کلاس تکمیل یک جریان سادهٔ واریز، برداشت و پرداخت است، نه اتصال به درگاه واقعی.
الگو: [Attachment](../attachments/readme.md).

## جدول تسک‌ها

| تسک | وضعیت | شاهد / کار باقی‌مانده |
|---|---|---|
| ساختار entityهای مالی | انجام‌شده | Bank، BankAccount، Cashier، Transaction و ارث‌بری JOINED پرداخت |
| حذف لیست‌های معکوس و انتقال enumها | انجام‌شده | مدل ساده‌تر و entity/enums |
| حذف ستون فعال CVV2 | انجام‌شده | فیلد قدیمی CardPayment کامنت است |
| حذف شمارهٔ کامل کارت از مدل | انجام‌نشده | CardPayment هنوز cardNumber دارد؛ فقط چهار رقم آخر لازم است |
| مدل مبلغ و balance یکدست | انجام‌نشده | Payment.amount از نوع long و BankAccount.balance از نوع Long؛ قرارداد BigDecimal تکمیل نشده |
| هماهنگی enumها | ناقص | TYPE و STATUS اضافی در enumهای Payment باقی‌اند |
| soft delete در پرداخت JOINED | ناقص | SQLDelete روی ریشه هست؛ حفظ ردیف زیرکلاس‌ها در حذف باید عملاً بررسی شود |
| اسکلت repositoryهای مالی | انجام‌شده | کلاس‌ها موجودند، اما بعضی finderها ناقص‌اند |
| finder حساب بر اساس بانک | ناقص | `findByBank` entity bank را با bankId عددی مقایسه می‌کند |
| count حساب‌های بانک | انجام‌نشده | `BankAccountRepository.countByBank` مقدار null می‌دهد |
| DTOهای record و mapperها | ناقص | ساختار موجود؛ رابطه‌ها و قرارداد پرداخت‌ها یکدست نیستند |
| validation چهار رقم کارت | ناقص | regex فعلی `^{1,4}$` معتبر نیست؛ باید دقیقاً چهار رقم بررسی شود |
| ایجاد/خواندن حساب بانک | ناقص | repository/mapper وصل‌اند؛ رابطهٔ bank، موجودی اولیه و قواعد کامل نیست |
| ویرایش/حذف حساب و فیلتر بانک | انجام‌نشده | update/delete Optional خالی و findByBank لیست خالی می‌دهد |
| CRUD بانک و صندوق‌دار | انجام‌نشده | serviceها هنوز null، Optional خالی یا List خالی می‌دهند |
| ثبت واریز/برداشت و تغییر balance اتمیک | انجام‌نشده | TransactionService.register و findByBankAccount پیاده نشده‌اند |
| جلوگیری از برداشت بیشتر از موجودی | انجام‌نشده | exception موجود است، ولی فرایند register خالی است |
| پرداخت نقدی/کارتی/چکی | انجام‌نشده | متدهای service هنوز stub هستند |
| خواندن همهٔ پرداخت‌ها/سفارش | انجام‌نشده | PaymentServiceImpl متدهای خالی دارد |
| CDI سرویس پرداخت | انجام‌نشده | PaymentServiceImpl annotation scope ندارد |
| exceptionهای business | ناقص | چند کلاس وجود دارد؛ قواعد هنوز به service متصل نشده و DuplicateAccountNumberException وجود ندارد |
| APIهای خواندن اولیه | ناقص | بیشتر فقط GET؛ BankAccountApi مقدار null می‌دهد |
| APIهای CRUD، paging و عملیات چک | انجام‌نشده | endpointهای نوشتن و clear/bounce تکمیل نشده‌اند |
| یکدست‌سازی مسیرها و تزریق interface | ناقص | مسیرهای قدیمی و بعضی scope/injectionها باقی‌اند |
| UI فهرست و پیش‌نمایش فرم | انجام‌شده | ۸ صفحهٔ مالی با readOnly؛ تضمین دریافت دادهٔ واقعی نیست |
| فعال‌سازی نوشتن UI مالی | انجام‌نشده | فقط پس از تکمیل API و قواعد service |
| تست خودکار و بررسی HTTP | انجام‌نشده | تست مالی وجود ندارد و deploy در این نوبت انجام نشده است |

«انجام‌شده» فقط وجود پیاده‌سازی مشخص را بیان می‌کند؛ این ماژول آمادهٔ
تراکنش مالی واقعی نیست. کامپایل موفق، متدهای stub و validation زمان اجرا را نمی‌سنجد.

## مسیرهای موجود

همه پس از `/api/v1` هستند و فعلاً تنها APIهای اولیهٔ خواندن‌اند.

| بخش | مسیر فعلی |
|---|---|
| بانک | `/banks` |
| حساب | `/bankaccounts` |
| صندوق‌دار | `/cashiers` |
| پرداخت | `/payments` |
| نقدی | `/payments/cashs` |
| کارتی | `/payments/cards` |
| چکی | `/payments/cheques` |
| تراکنش | `/transactions` |

این‌ها مسیرهای فعلی‌اند، نه مسیرهای نهایی دستور کار قبلی.
تغییر مسیر باید هم‌زمان با modules.js هماهنگ شود.
readOnly در UI هیچ عملیات نوشتن را ارسال نمی‌کند.

## ترتیب تکمیل آموزشی

۱. **بانک و حساب:** CRUD، کد/شمارهٔ تکراری، bankId موجود، mapping relation
و جلوگیری از حذف بانک دارای حساب. حساب جدید با موجودی صفر ساخته شود.
۲. **صندوق‌دار:** CRUD و کد کارمند تکراری.
۳. **گردش حساب:** فقط خواندن و ثبت؛ DEPOSIT اضافه و WITHDRAW کم کند.
ثبت transaction و تغییر balance در یک transaction باشند؛ برداشت بیش از موجودی رد شود.
۴. **پرداخت:** فقط شمارهٔ سفارش نگه‌داری شود؛ خروجی مشترک PaymentDto.
نقدی/کارتی با COMPLETED و چک با PENDING ساخته شود؛
clear/bounce فقط برای چک PENDING مجاز باشند.
۵. **قرارداد و امنیت داده:** مبلغ BigDecimal، شناسه به‌جای entity، فقط چهار رقم
آخر کارت؛ mapping و constraintها با Request هماهنگ شوند.
۶. **REST و UI:** scopeها و interface injection، 400/404/409، paging و
مسیرهای نوشتن تکمیل شوند؛ سپس readOnly مالی برداشته شود.
۷. **تست:** موجودی پس از چند گردش، انتقال وضعیت چک، finderها و حذف نرم JOINED بررسی شوند.

برای این پروژه اتصال بانکی، پرداخت آنلاین، event bus و معماری مالی پیچیده اضافه نکنید.

## نتیجهٔ بررسی

کامپایل و package با `-DskipTests` در ۲۰۲۶/۱۰/۱۳ موفق شد.
هیچ تست مالی در Surefire اجرا نشده است. ساخت WAR به معنی deploy موفق CDI،
درست‌بودن regex، ذخیرهٔ پرداخت یا تغییر balance نیست.
در این نوبت هیچ متد، DTO، entity یا تنظیمی اصلاح نشده است.
