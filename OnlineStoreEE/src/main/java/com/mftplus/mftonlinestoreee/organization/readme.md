# سازمان، شعبه و دپارتمان

ساختار فعلی: `Organization → Branch → Department`.
کارمندان در Department نگه‌داری می‌شوند، نه Branch؛
دستور کار قدیمی کارمندان شعبه با این مدل جایگزین شده است.
وابستگی به User فقط برای کارمندان است.
الگو: [Attachment](../attachments/readme.md).

## جدول تسک‌ها

| تسک | وضعیت | شاهد / کار باقی‌مانده |
|---|---|---|
| entityهای سازمان، شعبه و دپارتمان | انجام‌شده | BaseEntity، soft delete، رابطه‌های Lazy و مقدار اولیهٔ وضعیت |
| جدول واسط کارمندان دپارتمان | انجام‌شده | رابطهٔ Department.employees با User |
| repositoryهای finder و count | انجام‌شده | شمارهٔ ثبت، کد شعبه، دپارتمان‌های شعبه، کارمند و count وابستگی‌ها |
| DTO بدون entity و mapper رابطه‌ها | انجام‌شده | شناسه/نام سازمان و شعبه؛ status توسط service مدیریت می‌شود |
| CRUD و paging هر سه بخش | انجام‌شده | serviceهای واقعی و REST |
| شمارهٔ ثبت و کد شعبهٔ تکراری | انجام‌شده | کنترل در service بین رکوردهای حذف‌نشده |
| کد دپارتمان یکتا در شعبه | انجام‌شده | `findByBranchIdAndCode` و helper service |
| والد موجود و فعال | انجام‌شده | شعبه برای سازمان فعال؛ دپارتمان برای شعبهٔ فعال |
| جلوگیری از حذف والد دارای فرزند | انجام‌شده | سازمان دارای شعبه / شعبه دارای دپارتمان رد می‌شوند |
| فعال/غیرفعال‌کردن | انجام‌شده | عملیات جدا برای سازمان، شعبه و دپارتمان |
| خواندن/افزودن/حذف کارمند | انجام‌شده | User ناموجود رد و عضویت تکراری اضافه نمی‌شود |
| transaction برای mapping رابطهٔ Lazy | انجام‌شده | service شعبه/دپارتمان و DepartmentDtoLoader |
| کش findById سازمان و دپارتمان | انجام‌شده | RedisDtoCache؛ فهرست و paging کش نمی‌شوند |
| ابطال کش پس از commit | انجام‌شده | تغییر/حذف/وضعیت؛ ویرایش شعبه تمام DTOهای دپارتمان را پاک می‌کند |
| UI هر سه بخش و عملیات کارمند | انجام‌شده | metadata و فرم‌ها در modules.js |
| تست خودکار CRUD و قواعد | انجام‌نشده | تست organization وجود ندارد |
| تست کش، rollback و قطعی Redis | انجام‌نشده | [کارهای کش](cache/readme.md) |
| بررسی نسخهٔ فعلی روی TomEE | انجام‌نشده | در این نوبت deploy و تست HTTP انجام نشده است |
| تعیین و بررسی مجوز APIها | انجام‌نشده | این APIها سیاست annotation یکدست ندارند؛ زیرساخت امنیت نیز ناقص است |

«انجام‌شده» یعنی کد موجود است؛ تست یا تأیید رفتار سرور جداگانه لازم است.

## مسیرهای فعلی

همه پس از `/api/v1` هستند.
برای هر یک از `/organizations`، `/branches` و `/departments`:
GET/POST روی collection، GET/PUT/DELETE روی `/{id}` و GET روی `/page` وجود دارد.

| عملیات ویژه | HTTP و مسیر |
|---|---|
| شعبه‌های سازمان | GET `/organizations/{id}/branches` یا `/branches?organizationId=1` |
| دپارتمان‌های شعبه | GET `/branches/{id}/departments` یا `/departments?branchId=1` |
| دپارتمان‌های کارمند | GET `/departments?userId=1` |
| وضعیت | POST `/{resource}/{id}/activate` و `/deactivate` |
| کارمندان دپارتمان | GET `/departments/{id}/employees` |
| افزودن کارمند | PUT `/departments/{id}/employees/{userId}` |
| حذف کارمند | DELETE `/departments/{id}/employees/{userId}` |

در سطر وضعیت، resource یکی از organizations، branches یا departments است.
تغییر عضویت کارمند کش DTO را باطل نمی‌کند، چون DepartmentDto فهرست کارمندان ندارد.

## ادامهٔ کار آموزشی

۱. تست قواعد تکرار، والد غیرفعال و حذف والد دارای فرزند را بنویسید.
۲. CRUD و وضعیت‌ها را روی TomEE و UI بررسی کنید.
۳. سناریوهای کش و امنیت را جدا از تست‌های business بررسی کنید.
نیازی به کش شعبه، لیست‌ها یا الگوریتم هماهنگی پیچیده برای این مثال نیست.

## نتیجهٔ بررسی

کامپایل و package با `-DskipTests` در ۲۰۲۶/۱۰/۱۳ موفق شد.
هیچ تست خودکار این ماژول یا Redis در suite فعلی اجرا نشده است.
در این نوبت فقط مستندات تغییر کرده‌اند.
